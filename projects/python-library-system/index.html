05 / Build notes

Implementation

01

Book model

book.py defines a Book class with ISBN, title, author, genre, and availability. Getters, setters, borrow_it(), and return_it() manage those values.

02

Catalogue operations

library_app.py contains loading, ISBN lookup, add/remove, menu, and save functions. The loader reads comma-separated records into Book objects.

03

Collaborative development

The repository represents a three-person academic team project. Because the source does not attribute individual functions, this portfolio does not claim sole ownership of specific modules.

06 / Diagnostic reasoning

Troubleshooting

01

Code-review finding

The original application stored the selected catalogue filename in local scope while the save path referenced it elsewhere. During the portfolio refresh, I traced the data flow and corrected the design by passing the filename explicitly to the save function.

02

Retest approach

After the change, the repository was refreshed with a working menu flow, a sample catalogue, and repeatable assertions for the Book model so the core behaviours can be checked consistently.

07 / Verification

Validation

01

Book model checks

The refreshed test_book.py uses assertions to verify construction, borrowing, title matching, returning, setters, and genre handling.

02

Application validation

The refreshed repository also includes a small sample catalogue and an explicit load/save path so the command-line workflow can be exercised locally without relying on hidden files.

08 / Reflection

What I Learned

01

OOP and maintainability

The project reinforced separating data and behaviour into a reusable class, keeping catalogue operations in application functions, and using repeatable tests when changing program behaviour.

02

Team-code review

Working from a shared codebase also highlights the value of clear ownership, consistent naming, scoped variables, and tests that make integration problems easier to diagnose.
